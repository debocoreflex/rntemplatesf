# 🗂️ DatabaseLayer – Generic Repository Architecture

This `DatabaseLayer` provides a **database-agnostic abstraction layer** for querying and manipulating data from any backend like:

- 📦 Salesforce SmartStore (Soup)
- 🧮 Realm DB
- 🧠 Salesforce SOQL API
- 📊 SQLite / custom DBs (future support)

This architecture follows the **Repository Pattern**, decoupling the app’s business logic (e.g. ViewModels) from the specific database implementation.

---

## 📁 Folder Structure

```

DatabaseLayer/
│
├── entities/
│   └── ContactEntity.ts               # Domain-level data structures
│
├── interfaces/
│   ├── IWrite.ts                      # Common interface for save/update/delete
│   ├── IQuery.ts                      # Common interface for read/query
│   └── GenericQueryParams.ts         # Generic, flexible query parameter interface
│
├── repository/
│   ├── BaseRepository.ts              # Core base class using GenericQueryParams
│   └── ContactRepository.ts           # Extends base for contact-specific logic
│
├── db-implementations/
│   ├── SmartStoreUtils.ts             # SmartStore query/save/delete logic
│   └── (optional) RealmUtils.ts       # Realm-specific operations

````

---

## 🧩 Components Explained

### 1. `GenericQueryParams.ts`

The **heart of the querying logic**. This flexible object defines all the possible querying needs — from full-text search to SOQL filtering — using a single consistent structure.

Example:
```ts
{
  table: 'contacts',
  fields: ['Id', 'Name'],
  filters: [['Department', '=', 'Engineering']],
  orderBy: 'LastName',
  limit: 50
}
````

---

### 2. `IQuery<T>` and `IWrite<T>`

These interfaces define the contract for your repositories:

* `IQuery<T>` handles reading/querying
* `IWrite<T>` handles save/update/delete

Each Repository implements these, so ViewModels only interact with **abstracted logic**, not DB-specific code.

---

### 3. `BaseRepository<T>`

A reusable class that implements `IQuery<T>` and `IWrite<T>` using:

* `GenericQueryParams`
* DB-specific utilities (SmartStoreUtils, Realm, etc.)

This is where query parsing, DB engine routing, and entity mapping happens.

---

### 4. `ContactRepository.ts`

A domain-specific extension of `BaseRepository<T>` for contacts:

```ts
export class ContactRepository extends BaseRepository<ContactEntity> {
  constructor() {
    super('contacts'); // soup/table name
  }
}
```

This allows you to inject **custom logic** for contact save/query, while still reusing all generic behavior from `BaseRepository`.

---

## 🔗 How It Links to ViewModel

### ✅ In ViewModel:

You **only pass raw domain data and params**. Example:

```ts
contactRepository.query({
  table: 'contacts',
  searchText: 'John Doe'
});
```

Or:

```ts
contactRepository.save([
  {
    Id: '123',
    Name: 'John',
    Department: 'Engineering'
  }
]);
```

The ViewModel doesn't care if the data is saved in SmartStore, Realm, or queried via SOQL. The database details are hidden inside the `BaseRepository`.

---

## 🔧 SmartStore/Query Logic

You can inject SmartStore logic like:

```ts
smartstore.querySoup(
  false,
  'contacts',
  smartstore.buildMatchQuerySpec(...),
  successCB,
  errorCB
);
```

From within `BaseRepository`, based on the params.

---

## 🧪 Extending for Realm / SOQL / SQL

To add another DB layer:

* Implement a new adapter in `db-implementations/RealmUtils.ts` (or similar)
* Route `GenericQueryParams` inside `BaseRepository` based on DB type
* Keep the interface stable — no changes needed in ViewModel

---

## 🏁 Final Benefits

* 🔄 Swap DB backends without rewriting ViewModel code
* 🧼 Centralized query/save logic
* 🔄 Consistent and stable `GenericQueryParams` shape
* ✅ Ideal for offline-first apps with sync later capabilities

---

> This architecture empowers clean separation of concerns between your ViewModel (app logic) and your database engine, future-proofing your codebase.
